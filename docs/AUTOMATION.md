# 管理员自动化执行

网页可将当前编排或导入的英文 JSON 提交给服务器，由已有 `lab_automation.Runner` 实际执行泵阀动作。仅管理员可准备、启动与停止；观测员可以查看方案、运行状态、历史与实时推送。

## 网页操作

1. 加载已有方案，或导入 JSON 后检查动作与参数。方案可以先保存；本次运行也支持尚未保存的有效编排。
2. 管理员点击“运行当前编排”。后端编译全部动作，将方案、设备模板、展开后的计划保存为独立快照。此时不打开串口。
3. 检查确认框中的设备、液体、体积、废液通道和转速。包含注射泵时，先完成本次回零校验；然后在“启动前排空”中显式选择废液 1 或废液 2，确认接液条件并执行排空。
4. 排液动作成功结束后，现场检查电解池。若仍有残液，可再次执行排空；确认已空后勾选并点击“确认空池”。只有本次回零（如需要）和空池准备均通过，才允许“确认启动设备”。方案、模板或安全策略改变后需要重新准备。
5. 后端检查串口节点、占用与权限，然后在独立控制进程中对所有参与设备进行预检。全部通过后才执行第一步动作。
6. 页面按秒显示当前设备、步骤、目标体积、估算进度与耗时。运行结果保留在状态栏和历史记录；体积与进度不是独立传感器测量值。

“停止当前实验”会向本次控制进程发送终止请求，由现有控制器停止正在动作的设备并关闭串口。界面先显示等待停止反馈，收到清理结果后才显示结束。设备停止回读失败会标记异常，需要现场确认。

## 每次实验的注射泵回零校验

这里的校验指机械归零、零位与状态核验；液体体积仍使用现有注射器容量和步数换算，不会重新测量流量。

每个包含 `syringe_c` 的新实验准备记录都从“未校验”开始。独立的校验进程只操作这台注射泵：先读取状态、核验配置的设备身份，再发送完整的 `ZR`，等待完成，验证位置为 0、阀位有效、缓冲区为空、设备就绪且错误码为 0。管理员确认回零排液条件是接口的必要字段，普通账号不能触发。

依据随设备提供的 SY11 说明书第 4.3.1、4.4、4.5.5、4.5.7 和 4.6 节，完整的新指令串会覆盖未执行的旧缓冲；回零只发送完整 `ZR`，不会单独发送可能恢复中止程序的 `R`，也不使用软件置零 `z`。错误码 7 表示设备未初始化；`Q=0` 只表明当前未报告错误，不能代替机械回零证据。

校验结果仅绑定本次准备记录，启动后即消耗。另一个新实验不能借用前一次结果；校验失败、中止、过期、其他控制操作或重新准备后均须重新校验。设备重新上电后请重新准备并回零，软件不能只依靠 `Q=0` 判断设备是否经历过断电。网页同时显示最近回零时间和本次实验的独立校验状态。

校验失败不会启动实验其余泵阀，也不会自动重试。校验过程与正常实验共用串口互斥和管理员停止机制，所有动作和校验绑定关系均留在本机审计及运行记录中。

切换页面、关闭浏览器、退出登录或会话过期均不会重启任务，也不会直接停止服务器上的任务。重新登录后可以继续监测；另一管理员也可以请求停止。重复提交相同运行 ID 不会再执行一次。

## 支持范围

目前支持已实现的蠕动泵注入、抽出、切换阀、注射泵先吸入再注入以及控制器支持的等待动作。参数范围、流量换算、废液流路与注射泵行程均沿用现有控制器校验。

电化学工作站尚未集成，CV 仍支持编辑与保存。含测量动作的方案会整体拒绝启动，不会自动跳过测量去执行其余泵阀动作。

## 电解池容量和启动前准备

`config/safety_policy.json` 是后端权威安全策略，使用英文配置。当前电解池容量为 40 mL，水、硫酸、电解液以及其他注入液体全部合计。校验从本次已确认的空池开始，逐步累加注入、扣除标称抽出，余额最低为 0。超量抽出不产生负体积；整套实验累计注入量可以超过 40 mL，但任意一步之后的预计存量都不能超过 40 mL。已知注射泵步数取整造成的额外体积会保守计入。

前端在每步显示预计池内存量；后端在预演、保存、准备、启动和执行器入口校验容量。执行过程只接受与冻结计划一致的步骤，安全策略在运行中改变会在下一步动作前中止。客户端不能通过修改提交的 JSON、添加跳过参数或旧准备记录绕过安全策略。

每次实验另有固定的启动前排空动作：切换至管理员选定的废液流路，使用排液泵抽出标称 40 mL，并继承设备模板中的额外抽液时间。该动作不自动修改用户方案 JSON；方案中原有排液步骤仍会执行。

计时抽液不能证明实际液位，当前没有液位传感器。因此排空动作完成后只标记“待现场确认”，必须由管理员确认电解池已空，才能放行。接口记录人工确认者、时间、所属实验和排空记录，始终标注 `volume_measured=false`，不冒充液位实测。

建议先完成注射泵回零，再排空并确认；如果先排空再回零，回零会使原空池准备失效，需要再次排空确认。每个实验的准备记录独立绑定，失败、停止、过期、其他控制操作或重新准备后都不能复用。重复排空请求使用幂等标识；同一请求即使网络重试也不会再次动作，主动“再次排空”会产生新标识。

## 服务器配置

实际配置位于被 Git 忽略的 `config/server.json`。连接真实仪器时，将 `lab_root` 设置为已有控制工程目录，保持认证与 HTTPS 设置，并显式启用：

```json
{
  "hardware_execution_enabled": true,
  "automation": {
    "prepare_ttl_seconds": 600
  }
}
```

以上是需要合并的配置片段。公共示例与本机合成演示默认保持 `hardware_execution_enabled=false`。真实执行要求 Linux、支持 PID 句柄的 Python 和现有控制器的串口依赖；网页服务账号应具备相应串口的访问权限。

运行快照与进程记录保存在 `data/executions/<run-id>/`，原始控制事件保存在控制工程的 `logs/automation/run-<run-id>.jsonl`。目录、设备配置、操作者和日志只留在服务器，不上传 Git。网页不会覆盖原方案来执行，也不会修改硬件动作模板。

控制进程与原命令行控制器、状态查询共用 `execution.lock`。执行期间的状态刷新只读取事件，不另外打开串口。网页服务重启后可识别仍在运行的同一进程；停止只针对已记录且身份匹配的控制进程，不接收客户端 PID 或命令。

## 接口与权限

| 方法 | 路径 | 权限 | 请求 |
| --- | --- | --- | --- |
| GET | /api/execution | 登录用户 | 当前状态与可用能力 |
| POST | /api/execution/prepare | 管理员 | sequence |
| POST | /api/execution/start | 管理员 | run_id、version |
| POST | /api/execution/calibrate | 管理员 | run_id、version、confirm_discharge=true |
| POST | /api/execution/drain | 管理员 | run_id、version、route、confirm_discharge=true、request_id |
| POST | /api/execution/confirm-empty | 管理员 | run_id、version、empty_confirmed=true |
| GET | /api/execution/preparations/{run_id} | 登录用户 | 本次准备的校验状态 |
| POST | /api/execution/stop | 管理员 | run_id |
| GET | /api/events | 登录用户 | SSE 状态流 |

写入接口要求有效会话、CSRF、请求保护头与同源校验；执行请求和接受结果记录到现有审计库。客户端不能指定程序、路径、命令行、设备配置或任意串口报文。

## 验证

执行相关测试只使用临时账号、合成模板和虚拟串口，真实 Python 驱动会与虚拟泵阀对话。测试覆盖五设备完整流程、空注射器先吸入再注入、逐步进度、SSE、预检失败阻止所有泵动作、重复启动、互斥、停止清理、停止回读失败、会话权限与进程身份保护。部署检查不启动真实实验。
